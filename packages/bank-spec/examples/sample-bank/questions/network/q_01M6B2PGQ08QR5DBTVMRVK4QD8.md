## 一句话
用 STAR 结构讲清背景、你的职责、排查步骤与证据、结果和复盘改进，重点体现定位思路而不是堆砌工具名。

## 要点
- [kp1|2] 背景量化：影响范围、超时比例、持续时间
- [kp2|3] 排查有层次：先止血，再按链路逐段缩小范围，结论有数据支撑
- [kp3|2] 讲清根因与修复，以及如何验证修复有效
- [kp4|2] 复盘改进：监控告警、超时与重试配置、预案

## 详解
### 回答结构（STAR）
- **S 情境**：什么系统、什么时间、影响多大（如「下单接口 P99 从 200ms 升至 5s，超时率 8%」）；
- **T 任务**：你在其中的角色与目标；
- **A 行动**：按时间线讲排查过程；
- **R 结果**：恢复时间、指标变化、后续改进。

### 排查思路示例
1. **止血**：确认是否与最近发布相关，必要时回滚或扩容；
2. **定位层级**：用链路追踪看耗时落在网关、应用、下游服务还是数据库；
3. **找证据**：线程 dump 发现大量线程阻塞在获取数据库连接，连接池耗尽；
4. **根因**：一个下游 HTTP 调用没有设置超时，在持有数据库事务时长时间等待；
5. **修复**：给所有外部调用设置连接与读取超时，把远程调用移出事务。

### 面试官关注点
是否独立思考、能否用数据验证假设、是否做了防止复发的改进。

## 易错点
- 只罗列工具，说不清每一步为什么这么做
- 没有量化结果
- 把功劳全归自己或把问题全推给别人

## 追问
### [f1] 如果再遇到类似问题，你会如何更快发现？
为关键接口配置基于 P99 与错误率的告警；对连接池使用率、线程池队列长度做监控；统一治理外部调用的超时、重试与熔断配置，并在压测中覆盖下游变慢的场景。
