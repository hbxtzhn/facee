## 一句话
七个参数决定线程数、队列与拒绝方式；提交任务时依次判断核心线程、工作队列、最大线程，都满则执行拒绝策略。

## 要点
- [kp1|2] corePoolSize、maximumPoolSize、keepAliveTime 与 unit 控制线程数量
- [kp2|2] workQueue 存放等待任务，threadFactory 创建线程，handler 处理拒绝
- [kp3|3] 流程：先建核心线程，再入队列，队列满才扩到最大线程，最后拒绝
- [kp4|2] 默认拒绝策略是 AbortPolicy，抛出 RejectedExecutionException
- [kp5] 无界队列会让 maximumPoolSize 失效，并可能导致 OOM

## 详解
### 执行流程
1. 运行线程数 < `corePoolSize`：新建线程执行该任务（即使有空闲线程）；
2. 否则尝试放入 `workQueue`；
3. 队列已满且线程数 < `maximumPoolSize`：新建非核心线程执行该任务；
4. 否则交给 `RejectedExecutionHandler`。

非核心线程空闲超过 `keepAliveTime` 会被回收；`allowCoreThreadTimeOut(true)` 时核心线程也会回收。

### 四种内置拒绝策略
- `AbortPolicy`：抛异常（默认）；
- `CallerRunsPolicy`：由提交任务的线程自己执行，起到反压作用；
- `DiscardPolicy`：静默丢弃；
- `DiscardOldestPolicy`：丢弃队列头部最旧的任务后重试提交。

### 为什么不建议用 Executors
`newFixedThreadPool` / `newSingleThreadExecutor` 使用无界 `LinkedBlockingQueue`，任务堆积可能 OOM；`newCachedThreadPool` 最大线程数为 `Integer.MAX_VALUE`，可能创建过多线程。

## 示例
```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        8, 16,
        60, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000),
        r -> new Thread(r, "order-worker"),
        new ThreadPoolExecutor.CallerRunsPolicy());
```

## 易错点
- 以为任务先扩到最大线程数再入队列，顺序正好相反
- 使用无界队列却期望 maximumPoolSize 生效
- 不给线程命名，排查问题时难以定位

## 追问
### [f1] 核心线程数怎么估算？
CPU 密集型约为 CPU 核数 + 1；IO 密集型可按「核数 × (1 + 等待时间 / 计算时间)」估算。估算只是起点，最终要靠压测和监控（活跃线程数、队列长度、拒绝次数）调整，最好支持动态修改。
